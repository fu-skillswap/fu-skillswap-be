# Prompt 13 — FPTU legacy dependency audit and CONTRACT cleanup blueprint

## Scope and evidence

Read-only audit performed against the current source tree. No production behavior, migration, schema, seed data, or tests were changed for this audit. The working tree already contains uncommitted Prompt 11/12 changes; those were preserved.

Evidence sources: `rg` across `src/main/java`, `src/test/java`, `src/main/resources/db/migration`, and `docs`; controller-to-service-to-port/repository/DTO tracing for identity, mentor, payment/campaign, forum, and catalog paths; direct inspection of V1, V21, V35, V37, V39, V72, V97, V137, and V138. Current maximum Flyway version is **V138**, so the next version reserved for Prompt 14 is **V139**. Do not edit historical migrations.

Action values in this report are exclusive: `DELETE`, `REWRITE`, `DEPRECATE`, `BLOCKED`.

### Recommendation and campaign decision

Recommendation has non-education signals today: rating/review/session quality, capability/subject fit, service, availability, duration, and activity. Prompt 14 should remove education from recall and scoring/reason text, keep only already-existing useful non-education signals, and keep deterministic tie-breaks. If those signals are not used, return simple deterministic eligibility ordering; do not build a new recommender.

Campaign matching is a live financial-benefit consumer. The three configured legacy dimensions currently gate whether credit applies. Inventory ACTIVE and scheduled campaign audience sets before rollout. Prompt 14 must not translate legacy IDs to canonical IDs. Either explicitly clear/retire these dimensions under an approved campaign policy, or keep the deployment blocked until the affected campaign benefit behavior is resolved. Role targeting remains valid.

### MSSV decision

The search found no verification, authorization, eligibility, or matching behavior using MSSV; V13 removed the legacy verification column/flow for verified codes, and current typed requests ignore/deprecate `studentCode`. The remaining `student_profiles.student_code` column is read/written for legacy owner profile and admin display only. It is optional and has no demonstrated active business purpose. Prompt 14 should remove the API fields, admin projection, demo fixtures, entity mapping, and DB column after the documented client transition; do not make it required or backfill it from another identifier.

## Task 2 — FTS audit and V139 CONTRACT blueprint

### Consumers versus maintenance

Static application search found **no query consumer** of `MentorProfile.searchDocument`, `search_document`, `search_vector`, or PostgreSQL `@@`/`tsvector` search. Prompt 12 search calls `MentorProfileRepository.findDiscoverableCandidateIds[WithKeyword]`; keyword predicates use current mentoring text and `translate(...) LIKE`, never either search column. Recommendation recall and score also do not query FTS. No scheduled job reads these artifacts.

The mapped `MentorProfile.searchDocument` is not read by a Java mapper/repository and has no application setter call. The database chain still writes/refreshes these fields:

* V21 creates `search_vector`, GIN `idx_mentor_profiles_search_vector`, `mentor_profiles_fts_update()` and `trg_mentor_profiles_fts` for headline/expertise/supporting subjects.
* V35 changes accent normalization in `mentor_profiles_fts_update()` and repopulates `search_vector`.
* V37 adds `search_document`, `skillswap_normalize_search_text(text)`, `refresh_mentor_profile_search_index(uuid)`, `refresh_mentor_profiles_by_tag(uuid)`, and trigger helpers. Its payload includes name/headline/expertise/supporting subjects/bio **and legacy campus/program/specialization names**, plus tags/services/service tags.
* V37 trigger set: `trg_mentor_profiles_search_refresh`, `trg_users_search_refresh`, `trg_student_profiles_search_refresh`, `trg_mentor_tags_search_refresh`, `trg_mentor_services_search_refresh`, `trg_mentor_service_help_topics_search_refresh`, `trg_tags_search_refresh`.
* V39 extends the payload with subject results, projects and achievements and attaches `trg_mentor_subject_results_search_refresh`, `trg_mentor_featured_projects_search_refresh`, `trg_mentor_achievements_search_refresh` using helper `trg_refresh_mentor_profile_search_from_subject_result()`.
* V97 drops/recreates `refresh_mentor_profile_search_index(uuid)` after help-topic cleanup. Its current payload still joins campus/program/specialization and still maintains search_document/search_vector.

Therefore these artifacts are **write/refresh only**, with no live read consumer. FTS non-education terms are present in the materialized payload, but there is no current endpoint/job consuming that index. Do not retain its triggers just because the payload includes useful text. Prompt 14 may drop the entire chain after the no-query proof is kept in its migration review. If a future search chooses FTS, it should be a new explicit feature, not an implicit reason to retain legacy refresh work.

### V139 CONTRACT order (proposed; no migration created)

1. **Resolve live business policies before DDL.** Inventory active/scheduled campaigns containing any legacy audience set and record approved retire/clear behavior. Confirm clients of public mentor compatibility fields, identity legacy APIs, admin summaries, and forum `authorProgram`. If any campaign would silently lose an advertised credit, do not proceed until resolved.
2. **Rewrite live consumers in code first within the same release.** Recommendation loses all education recall/score/reason dependencies; campaign matcher/admin surface loses legacy dimensions under the policy from step 1; forum drops program-based priority and response snapshot; admin/identity/public response mappers stop reading legacy entity associations; legacy student update path is removed or narrowed so it cannot write fields that will be dropped. Keep canonical identity, school/alumni distinction and `profileType == null` incomplete invariant.
3. **Remove/deprecate public contracts and application mappings.** Remove card/detail compatibility education members only after client migration; remove legacy catalog endpoints/request/response properties; remove studentCode from owner/admin DTOs and request; update OpenAPI, frontend guide, seeders, tests, and JPA `StudentProfile`/`Campaign`/`ForumPost` mappings. Keep canonical education detail and canonical catalog endpoints. Remove `MentorDiscoveryQueryRow` legacy projection arguments and `DiscoveryEducationPolicy`/education recommendation reason codes after all call sites are gone.
4. **Drop FTS triggers before functions/columns.** Explicitly `DROP TRIGGER ... ON ...` for every V21/V37/V39 trigger listed above. Then drop helper functions in dependency order: `trg_refresh_mentor_profile_search_from_*`, `refresh_mentor_profiles_by_tag(uuid)`, `refresh_mentor_profile_search_index(uuid)`, `mentor_profiles_fts_update()`, `skillswap_normalize_search_text(text)`. Drop `idx_mentor_profiles_search_vector`; then drop `mentor_profiles.search_document` and `search_vector`. Prefer plain `DROP FUNCTION` after trigger removal; do not use `CASCADE`.
5. **Drop child constraints/indexes and referencing snapshots/collections.** Drop `fk_forum_posts_author_program`, then forum program index, then `forum_posts.author_program_id`. Drop `fk_student_profiles_campus/program/spec`, and corresponding old profile indexes. Drop campaign audience legacy collection tables after campaign entity and API fields have been removed; keep role collection.
6. **Drop `specialization_tags` before `specializations`; then old profile FKs/columns.** Explicitly drop the specialization join table and its constraints/indexes. Drop `student_profiles.campus_id/program_id/specialization_id/semester/is_alumni/student_code/intake_year` after all code, FKs, and legacy contract dependencies are gone. Keep `graduation_year`, bio, and canonical catalog references.
7. **Drop legacy master data last.** Drop `campuses`, `specializations`, and `academic_programs` only after checking remaining FKs and all app/schema consumers. `academic_programs` also has historical/adjacent references: forum (removed in step 5) and possible campaign collections (removed in step 5); search remaining constraints via PostgreSQL catalog query and repository-wide static search. Keep the tag catalog itself; remove only `specialization_tags` mapping.
8. **Remove legacy seed/fixtures/docs** in application/test resources and refresh the OpenAPI/frontend guide. Retain a dedicated pre-V139 database fixture with representative legacy rows/FTS triggers for upgrade verification; it must validate that CONTRACT removes those objects and leaves canonical rows/data intact.

V37, V39, V97, V137, and V138 are **reference-only historical migrations**. Do not edit them. V139 should use direct, named drops with dependency order, not `DROP ... CASCADE`.

## Prompt 14 readiness gates

`READY_FOR_CONTRACT` means a migration plan exists; it is not permission to drop unresolved user-visible dependencies. Physical removal is allowed only when all of these are true:

1. No Java source, OpenAPI, frontend guide, seeder, runtime query, scheduled job, or active contract consumer reads/writes targeted legacy dimensions.
2. ACTIVE and scheduled campaign inventory proves legacy-targeted benefits are either deliberately retired/cleared with approved behavior or no longer at risk; no legacy ID is translated to institution/field group.
3. Mentor recommendation no longer queries or scores campus/program/specialization/semester/alumni; reason codes/text do not advertise those matches.
4. Forum feed/create/response no longer depends on `author_program_id` or AcademicProgram.
5. Identity legacy update/catalog paths and public/admin compatibility response consumers have completed the planned transition; no required data is inferred from legacy values. `profileType == null` continues to mean incomplete, even after its old academic details are gone.
6. MSSV is confirmed unnecessary by the current code/verification audit; all API/admin references removed before dropping `student_code`.
7. Fresh and V138 upgrade PostgreSQL tests pass, including retained-data assertions and explicit absence assertions for each dropped object.

If campaign inventory or a client/benefit policy is unresolved, Prompt 14 must stop before physical DDL and report `BLOCKED`; it may still deliver consumer rewrites and expand/contract preparation that do not drop the unresolved data.
