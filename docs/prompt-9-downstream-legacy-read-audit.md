# Prompt 9: downstream legacy read audit

## Scope and method

Audited `StudentProfile` reads by searching domain getters and database columns, then traced the resulting call sites through controller/service, port projection, repository JPQL/native SQL, DTO mapping, API docs, and relevant tests. The report does not change downstream production behavior. Profile types are never inferred from old catalog references or MSSV.

The current-profile types are `SCHOOL_STUDENT`, `UNIVERSITY_STUDENT`, and `ALUMNI`. A row with `profileType = null` remains legacy/incomplete even when old fields are populated. New profile saves clear the legacy campus/program/specialization/semester/intake/bio fields; MSSV is optional and is not a completion signal.

### Query and privacy trace notes

* `StudentProfileRepository.findWithDetailsByUserId` uses an entity graph for `user`, `campus`, `program`, and `specialization`; `findStudentProfilesByUserIdIn` is a bulk query without that graph, so any future loop mapping lazy legacy relations must use a bulk projection/fetch plan.
* Mentor discovery candidate filtering/counting uses native SQL over `student_profiles` legacy columns. Its count is separate from the candidate query; the row projection joins legacy catalog tables. The detail endpoint loads one profile with an entity graph, so legacy relation reads are not per-field N+1.
* `UserQueryPortImpl.toStudentProfileRecord` touches lazy legacy references; single-record reads use the entity-graph lookup, while callers of its bulk map method should be audited before adding loops. Current campaign matching reads one profile per checkout and does not expose the projection as an HTTP response.
* Booking and mentor verification consume only the `AcademicEligibilityQuery` completion boolean. Source search found no direct downstream student-profile reads in course, notification, or scheduled-job code beyond the enumerated identity completion and legacy semester maintenance paths. No student-profile export endpoint was found in the admin module.
* `studentCode` is not in mentor discovery/detail DTOs. The owner profile response retains it as the Prompt 7 compatibility field. Admin list/detail paths are admin-authorized; no policy bypass was found. Student profile GET resolves only the authenticated user's public ID.
* Search found no downstream canonical mapping of a school profile to campus/program. Canonical institution/province/field-group columns are not used by discovery filters, recommendations, forum prioritization, or campaign matching.

## Read-contract safety net added

`StudentProfilePostgresIntegrationTest.ownerReadContractKeepsLegacyCompatibilityFieldsOutOfCurrentProfileTypes` exercises the real PostgreSQL-backed owner read service for legacy, school, university, alumni, and another user. It checks legacy-only compatibility visibility, canonical values, optional nulls, and that current types do not get campus/program/specialization/studentCode/alumni compatibility values. `MentorDiscoveryServiceTest.getMentorDetail_currentSchoolProfileDoesNotProjectLegacyUniversityFields` guards the public mentor-detail compatibility projection and the null alumni semantics for current profile types. Existing `StudentProfileControllerTest` separately checks the wire DTO/OpenAPI compatibility fields and principal scoping at the controller boundary.
